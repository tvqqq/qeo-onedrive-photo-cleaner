# v0.3 Foundation — Schema & Source Identity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the persistent database to schema v3 and ingest Microsoft Graph `createdBy` / `lastModifiedBy` identity metadata so later tag search and Photo Detail work have stable storage and typed repository access.

**Architecture:** Perform one in-place v2→v3 migration that adds all v0.3 tag tables plus nullable source-identity columns. Extend the existing Graph delta item type/select list and `upsertPhoto()` mapping. Keep identity data best-effort: every scan reflects the current Graph response and missing components become `NULL`; never infer upload source from camera/path/name. Surface the new values through `PhotoRecord` and `PhotoMetadata`, but do not change Library behavior yet.

**Tech Stack:** TypeScript, Node 24, `node:sqlite`, Microsoft Graph v1.0, Vitest, Next.js 16.

**Spec:** `docs/superpowers/specs/2026-09-15-v0.3-library-actions-ai-tags-design.md`

## Global Constraints

- Use TDD for every behavior change: add a focused failing test, run it and confirm the intended RED failure, then implement the minimum GREEN change.
- Do not reset or replace `/data`; migration must preserve existing v2 records in place.
- Do not change OAuth permissions, duplicate-delete safety, worker-lane behavior, category semantics, or album-sync behavior in this plan.
- All ten source-identity columns are nullable. A missing identity component from a later Graph scan must overwrite the previous value with `NULL`, not preserve stale data with `COALESCE`.
- New installs must receive the complete v3 schema directly through `INITIAL_SCHEMA`; upgraded v1/v2 installs must reach the same schema through migrations.
- Commit after each GREEN task and run the targeted test before moving on.

```sql
CREATE TABLE IF NOT EXISTS tags (
  id TEXT PRIMARY KEY,
  slug TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS photo_tags (
  photo_id TEXT NOT NULL REFERENCES photos(id) ON DELETE CASCADE,
  tag_id TEXT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  confidence REAL,
  source TEXT NOT NULL CHECK(source IN ('ai','manual')),
  state TEXT NOT NULL CHECK(state IN ('active','removed')),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY(photo_id, tag_id)
);
CREATE INDEX IF NOT EXISTS photo_tags_tag_photo_idx ON photo_tags(tag_id, photo_id);
CREATE INDEX IF NOT EXISTS photo_tags_photo_state_idx ON photo_tags(photo_id, state);

CREATE TABLE IF NOT EXISTS photo_tag_state (
  photo_id TEXT PRIMARY KEY REFERENCES photos(id) ON DELETE CASCADE,
  tagged_etag TEXT,
  model_id TEXT NOT NULL,
  taxonomy_version TEXT NOT NULL,
  tagged_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS photo_tag_state_etag_idx ON photo_tag_state(tagged_etag);
```

- [ ] **Step 3: Replace the one-off migration guard with explicit migration lookup**

Use a version map or `switch` so both v2 and v3 are deliberate:

```ts
const MIGRATIONS: Record<number, string> = {

  3: MIGRATION_V3,
};

```
