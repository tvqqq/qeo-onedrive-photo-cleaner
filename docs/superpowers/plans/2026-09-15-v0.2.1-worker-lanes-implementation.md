# v0.2.1 Worker Lanes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prevent long-running ML jobs from blocking scans, make lane restarts safe, tolerate stale remote photos during similarity processing, and clarify queued scan UI state.

**Architecture:** Keep the existing SQLite jobs table, but make job claiming/requeueing lane-aware. Run one core worker (`scan`, `verify-exact`) and one ML worker (`classify`, `find-similar`) against the same `/data` volume. Introduce a typed Graph request error so only `404 itemNotFound` can be skipped safely by the similarity job.

**Tech Stack:** Next.js 16, TypeScript, Node 24, `node:sqlite`, Docker Compose, Vitest, Microsoft Graph.

**Spec:** `docs/superpowers/specs/2026-09-15-v0.2.1-worker-lanes-design.md`

## Global Constraints

- Preserve the current SQLite schema and `/data` volume.
- Core lane job types are exactly `scan` and `verify-exact`.
- ML lane job types are exactly `classify` and `find-similar`.
- Each worker process executes one job at a time; no intra-lane parallelism.
- Do not change exact-delete, similar-review, album-sync, or OAuth safety semantics.
- Do not include the existing `verify-exact` Graph 400 investigation in this change.
