# Qeo OneDrive Photo Cleaner v0.2 UI + Metadata Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade Qeo OneDrive Photo Cleaner with a polished hybrid dark UI, richer Graph-only photo metadata, and a paginated Photos browser without changing the existing deletion, classification, album-sync, or privacy safety model.

**Architecture:** Keep the existing Next.js App Router + SQLite + worker architecture. Extend the existing scan persistence with Microsoft Graph photo/image facets, introduce a focused `src/lib/photos` query/formatting module, and render the 20k+ photo library server-side in fixed-size pages; shared photo/UI primitives are reused by Photos, Duplicates, and Categories. Tailwind becomes the actual styling engine, while the existing local thumbnail API remains the only browser-facing image source.

**Tech Stack:** Node.js 24, Next.js 16.3.3 App Router, TypeScript 5.9, React 19.3, Tailwind CSS 4 via `@tailwindcss/postcss`, built-in `node:sqlite`, Microsoft Graph REST v1.0, Vitest + Testing Library, Docker Compose, GitHub Actions, Gitleaks.

**Spec:** `docs/superpowers/specs/2026-09-14-v0.2-ui-metadata-design.md`

## Global Constraints

- The app remains local-first, Docker-first, single-user, and Microsoft Personal Account-only.
- Do not download original files only to extract EXIF; v0.2 metadata comes from Microsoft Graph facets only.
- Do not add face recognition, identity clustering, cloud vision APIs, multi-user support, work/school-account support, public hosting, or Tailscale Funnel.
- Do not introduce shadcn or another broad component framework; use Tailwind plus small app-specific primitives.
- Exact duplicate semantics remain: `QuickXorHash + size` candidates → streamed SHA-256 verification → explicit user review → ETag preflight → normal Graph DELETE to OneDrive Recycle Bin.
- Never add a permanent-delete path.
- Similar-photo groups remain heuristic and review-only, with no delete controls and no automatic selection.
- Album sync remains add-only and only includes reviewed, non-deleted photos.
- OAuth remains `PublicClientApplication` + PKCE against the `consumers` authority, with no client secret.
- Browser clients must never receive Graph access tokens or Graph thumbnail URLs; thumbnails continue through the local `/api/thumbnails/[photoId]` endpoint and ETag-aware cache.
- Preserve all existing SQLite data during schema v1 → v2 migration; no reset or rebuild is allowed.
- Photos browsing must use server-side pagination; do not load the whole library into a browser request.
- Missing metadata is normal and is omitted from the UI rather than rendered as repeated `N/A` values.
- Do not display a fake scan percentage when Graph does not provide a reliable total.
- Existing worker runtime regression coverage must remain active.

- [ ] **Step 4: Make migration execution version-aware**

Refactor `migrateDatabase` so a clean database gets `INITIAL_SCHEMA` and version 2, while an existing v1 database gets only `MIGRATION_V2`:

```ts
if (currentVersion === 0) {
  db.exec(INITIAL_SCHEMA);
  db.prepare("INSERT INTO schema_migrations(version, applied_at) VALUES (?, ?)")
    .run(SCHEMA_VERSION, Date.now());
} else {
  for (let version = currentVersion + 1; version <= SCHEMA_VERSION; version += 1) {
    if (version !== 2) throw new Error(`Missing database migration for version ${version}`);
    db.exec(MIGRATION_V2);
    db.prepare("INSERT INTO schema_migrations(version, applied_at) VALUES (?, ?)")
      .run(version, Date.now());
  }
}
```

Keep the existing single `BEGIN IMMEDIATE` / `COMMIT` / `ROLLBACK` transaction around this logic.
