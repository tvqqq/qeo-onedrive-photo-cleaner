# Qeo OneDrive Photo Cleaner v0.2 — UI + Graph Metadata Design

**Date:** 2026-09-14
**Status:** Approved in chat, pending written-spec review
**Branch:** `feat/v0.2-ui-metadata`

## 1. Goal

Upgrade v0.1 from a functional maintenance UI into a polished local photo-management experience while keeping the same safety model. v0.2 adds a hybrid dark UI, richer Microsoft Graph metadata, and a new Photos browser for the indexed library.

The app remains local-first, Docker-first, single-user, and Microsoft Personal Account-only.

## 2. Non-goals

v0.2 will not:

- download originals only to extract EXIF;
- add face recognition or identity clustering;
- add cloud vision APIs;
- auto-delete similar photos;
- change exact-duplicate deletion safety;
- remove OneDrive album members automatically;
- expose the app publicly on the internet;
- add multi-user support or work/school account support.

## 3. UI Direction

Use a **hybrid UI**:

- Dashboard, Scan, and Settings use a compact dark productivity-dashboard style inspired by tools such as Linear: strong hierarchy, restrained cards, readable spacing, minimal visual noise.
- Photos, Duplicates, and Categories are photo-first: larger thumbnails, dense but readable metadata, and clear review actions.

### 3.1 Styling stack

Add Tailwind CSS as the actual styling engine. The current application uses many Tailwind-like utility class names without Tailwind being installed, so most of the intended styling is not applied.

Build a small internal UI primitive layer instead of adding a large component library:

- `AppShell`
- `PageHeader`
- `Card`
- `StatCard`
- `Badge`
- `Button`
- `PhotoCard`
- `MetadataRow`
- lightweight form/input/select primitives as needed

Keep these primitives focused and app-specific. Do not introduce shadcn or another broad UI framework in v0.2.

### 3.2 Global shell

Add a persistent desktop navigation shell with:

- Dashboard
- Photos
- Scan
- Duplicates
- Categories
- Settings

Use a compact top/side navigation that remains usable on tablets. Mobile support only needs graceful stacking; no separate mobile app behavior is required.

## 4. Graph Metadata Expansion

The scan remains Graph-only. No original-file download is performed for metadata extraction.

### 4.1 Existing metadata retained

Continue storing:

- Drive item ID
- name
- path
- size
- MIME type
- QuickXorHash
- ETag
- created date/time
- modified date/time
- capture date/time
- width
- height

### 4.2 New metadata

Extend `GraphDriveItem` and persistence to support:

From the Graph `photo` facet:

- `cameraMake`
- `cameraModel`
- `exposureNumerator`
- `exposureDenominator`
- `fNumber`
- `focalLength`
- `iso`
- `orientation`
- `takenDateTime`

From the Graph `image` facet:

- `width`
- `height`

The current implementation reads width/height from `photo`; v0.2 must use `image.width` and `image.height`, with a compatibility fallback to legacy `photo.width` / `photo.height` if older mocked/demo data still provides them.

Missing metadata is normal. The UI must hide absent fields rather than render repeated `N/A` placeholders.

## 5. Database Schema v2

Bump the SQLite schema version to v2 and migrate the existing `photos` table in place.

Add nullable columns:

- `camera_make TEXT`
- `camera_model TEXT`
- `exposure_numerator INTEGER`
- `exposure_denominator INTEGER`
- `f_number REAL`
- `focal_length REAL`
- `iso INTEGER`
- `orientation INTEGER`

Keep existing `width`, `height`, `taken_at`, `remote_created_at`, and `remote_modified_at` columns.

The migration must preserve all current indexed data, duplicate groups, classifications, settings, token cache files, and album-sync state.

A new Full Scan after upgrade is the supported way to backfill richer metadata for already-indexed photos.

## 6. Photos Browser

Add `/photos` as the main library inspection page.

### 6.1 Grid

Use a responsive thumbnail grid with approximately 60 photos per page. The server must never load the entire 20k+ library into memory for one request.

Each card shows, when available:

- thumbnail
- filename
- dimensions
- file size
- taken date
- camera make/model
- path, truncated visually but available in detail view

### 6.2 Search

Server-side search across:

- filename
- path
- camera make
- camera model

Use SQLite queries, not client-side filtering of all rows.

### 6.3 Filters

Support these initial filters:

- MIME type
- category
- captured date range

Do not add a general query-builder UI in v0.2.

### 6.4 Sorting

Support:

- capture date, newest/oldest
- modified date, newest/oldest
- size, largest/smallest
- name, ascending/descending

Default sort: capture date descending, falling back to modified date for photos with no capture timestamp.

### 6.5 Detail panel

Clicking a photo opens a detail panel/modal without navigating away from the result set.

Display only metadata that exists:

- full filename and path
- dimensions
- file size
- MIME type
- captured date/time
- created date/time
- modified date/time
- camera make/model
- ISO
- aperture (`f/<number>`)
- exposure (`numerator/denominator`, rendered as a human-readable shutter speed)
- focal length in mm
- orientation
- duplicate/hash status where useful

The detail panel is read-only in v0.2.

## 7. Duplicate Review UI

Reuse the shared photo-card primitives.

For exact duplicate groups, show larger thumbnails and enough metadata to make keeper decisions quickly:

- filename
- path
- size
- resolution
- taken timestamp
- camera make/model
- ISO / aperture / shutter / focal length where present
- verified SHA-256 state
- `Recommended keep` badge

Deletion semantics do not change:

1. QuickXorHash + size identify candidates.
2. streamed SHA-256 must match before a group is exact.
3. user explicitly selects delete candidates.
4. ETag is checked before deletion.
5. normal Graph DELETE sends items to OneDrive Recycle Bin.
6. no permanent-delete path is added.

Similar groups remain review-only and must not gain delete controls.

## 8. Category Review UI

Reuse the same shared photo-card presentation for consistency.

Show:

- thumbnail
- filename/path
- primary camera/capture metadata
- category chips
- confidence/source where relevant
- manual correction controls

Album sync behavior remains add-only and based on reviewed category assignments.

## 9. Dashboard Refresh

Rework the Dashboard to use the new shell and stat primitives.

Primary metrics:

- indexed photos
- indexed size
- exact groups to review
- potential reclaim

Secondary metrics:

- similar groups
- unreviewed classifications
- active job
- processed count

Add clear primary actions:

- Scan now
- Browse photos
- Review duplicates

Avoid decorative analytics or charts that do not help cleanup decisions.

## 10. Scan Page Refresh

Keep Full Scan and Incremental Scan behavior unchanged, but improve presentation:

- prominent job status
- processed count
- scan mode
- success/failure state
- concise explanation of Full vs Incremental

Do not invent a percentage when Graph does not provide a reliable total.

## 11. Settings Refresh

Group settings into clear sections:

- Microsoft connection
- runtime mode
- local data/model paths
- similar-photo thresholds
- cache controls

Preserve all existing behavior. Clearing thumbnail cache must remain isolated from the database and model cache.

## 12. Query and Indexing Strategy

Add only the SQLite indexes necessary for the new Photos page.

At minimum, evaluate indexes on:

- `taken_at`
- `remote_modified_at`
- `mime_type`
- `camera_make`
- `camera_model`

Filename/path text search can use `LIKE` in v0.2 because the library is around tens of thousands of rows. Do not introduce FTS unless profiling shows it is needed.

Category filtering should join `photo_categories` using existing keys/indexes; add a targeted index only if the query plan requires it.

## 13. Thumbnail Behavior

Continue using the existing local thumbnail API/cache.

Requirements:

- thumbnails lazy-load in grid/review views;
- the browser never receives Graph access tokens or Graph thumbnail URLs;
- cache invalidation remains tied to photo ETag;
- no prefetch of all thumbnails for the 20k+ library.

## 14. Error Handling

- Missing Graph metadata: silently omit the field.
- Thumbnail failure: render a neutral placeholder while preserving the card and metadata.
- Invalid Photos query parameters: normalize to safe defaults rather than issuing unsafe SQL.
- Empty search/filter result: render a useful empty state.
- Failed scan/backfill: preserve already-ingested metadata and show the existing job error state.

## 15. Worker Runtime Regression Protection

The worker startup fix merged before v0.2 must remain protected.

CI must validate both runtime processes:

- web container starts and responds to `/api/health`;
- worker process starts and remains alive long enough to prove there is no transform/startup failure.

The v0.2 UI work must not remove worker runtime coverage.

## 16. Security and Privacy

No security model changes are allowed in this release:

- `.env.local` and local data stay uncommitted;
- no client secret is introduced;
- OAuth remains PublicClientApplication + PKCE;
- originals remain in OneDrive;
- Graph metadata and thumbnails are cached locally under `/data`;
- no cloud vision provider is added;
- destructive actions still require explicit user review;
- Tailscale Serve remains the recommended remote-access mechanism; Funnel is not part of the app setup.

## 17. Testing Strategy

Use TDD for implementation work.

Required targeted coverage:

1. Graph metadata type/parsing tests.
2. image-facet width/height persistence test.
3. v1 → v2 migration test preserving existing data.
4. photo repository query tests for pagination.
5. search tests for name/path/camera.
6. filter tests for MIME/category/date.
7. sort tests for taken/modified/size/name.
8. metadata formatter tests for shutter/aperture/focal length/date handling.
9. Photos grid/detail component tests.
10. Duplicate card metadata tests.
11. Category card regression tests.
12. worker runtime regression test.
13. full lint/typecheck/test/build.
14. Docker web smoke + worker startup smoke.
15. Gitleaks.

## 18. Rollout

After merge:

1. `git pull` on the local Docker host.
2. `docker compose down`.
3. `docker compose up -d --build`.
4. Schema migration runs automatically on application startup.
5. Run one Full Scan to backfill new Graph metadata.
6. Use Incremental Scan afterward as normal.

No manual database reset is required or desired.

## 19. Acceptance Criteria

v0.2 is complete when all of the following are true:

- the application has a consistent polished dark UI across all existing pages;
- the Photos navigation/page exists and handles a 20k+ library through server-side pagination;
- photos can be searched, filtered, and sorted without loading the whole library in the browser;
- Graph-only camera/exposure metadata is persisted and displayed when available;
- image dimensions come from the Graph image facet;
- Duplicates and Categories show useful photo metadata in a photo-first layout;
- existing duplicate safety, album-sync safety, and Demo/Live behavior are unchanged;
- v1 local data upgrades to schema v2 without loss;
- worker startup remains covered and working in Docker;
- tests, lint, typecheck, production build, Docker smoke, and secret scan all pass.
