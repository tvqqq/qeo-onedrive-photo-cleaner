# v0.2.1 Worker Lanes Design

## Problem

Qeo currently has one restart-safe SQLite job queue and one worker loop. A long-running ML job (`classify` / `find-similar`) blocks operational jobs such as `scan` and `verify-exact`, so the Scan UI can remain `queued` even though the worker container is healthy. A restarted worker also requeues every running job globally. Separately, `find-similar` can fail after processing most of the library when a thumbnail fetch hits a Microsoft Graph `itemNotFound` for a photo that disappeared remotely.

## Approved design

Split execution into two worker lanes while keeping the existing SQLite jobs table and job types:

- **core lane:** `scan`, `verify-exact`
- **ml lane:** `classify`, `find-similar`

Docker Compose will run two worker services against the same `/data` volume. Each process receives an explicit `WORKER_LANE` and only claims/requeues jobs belonging to that lane. The repository remains the single source of truth for atomic claiming; no second queue system is introduced.

`find-similar` will treat Microsoft Graph `404 itemNotFound` while fetching a thumbnail as a stale remote photo: mark that drive item deleted locally, skip feature generation for that photo, advance progress, and continue. Other Graph failures remain fatal. This requires a typed Graph request error instead of parsing generic error strings.

The Scan UI will display queued jobs as **Waiting for worker** and running jobs as **Running**. No fake percentage will be added when the total is unknown.

## Safety constraints

- Do not change exact-duplicate deletion semantics, SHA-256 verification, ETag preflight, or Recycle Bin behavior.
- Similar groups remain review-only and non-destructive.
- Album sync remains add-only.
- Preserve the current SQLite database and `/data` volume; no destructive migration is required.
- Keep one process per lane; do not add parallel execution inside a lane.
- Do not fold the existing `verify-exact` Graph 400 investigation into this change.

## Acceptance criteria

1. A running `classify` job does not prevent a queued `scan` from being claimed by the core worker.
2. Core worker startup cannot requeue an ML job that is currently running, and vice versa.
3. A `find-similar` thumbnail fetch that fails with Graph `404 itemNotFound` skips/marks the stale photo and allows the job to continue.
4. Other Graph errors still fail the job.
5. Scan UI renders `queued` as `Waiting for worker` and `running` as `Running`.
6. CI verifies both worker lane containers stay running from the production Docker image.
