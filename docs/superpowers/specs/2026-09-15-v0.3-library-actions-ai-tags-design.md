# Qeo OneDrive Photo Cleaner v0.3 — Library Actions & AI Tags Design

## Status

Approved design for implementation planning.

## Goals

v0.3 turns the Photos/Library view into the primary place to organize and maintain individual photos while preserving the app's local-first and OneDrive-safe behavior.

The release adds four capabilities:

1. Add a photo to an existing OneDrive Photos album.
2. Generate local Qeo AI Tags for the whole library and use them for fast search/filtering.
3. Delete a single photo from Library with explicit confirmation and normal OneDrive Recycle Bin semantics.
4. Show best-effort OneDrive identity metadata describing which user, device, or application created/last modified an item.

## Non-goals

- Do not write or synchronize Qeo AI Tags into native OneDrive Photos tags.
- Do not create a new OneDrive album from the Library add-to-album flow.
- Do not add permanent-delete behavior.
- Do not infer an upload device from camera metadata, filenames, paths, or heuristics.
- Do not replace the existing category/classification subsystem; categories and tags remain separate concepts.
- Do not introduce cloud vision services. AI tagging remains local.

## Architecture Overview

The existing two-lane worker model remains unchanged:

- `core`: `scan`, `verify-exact`
- `ml`: `classify`, `find-similar`, new `tag-photos`

Scanning remains independent from AI work. A scan may enqueue follow-up tag work, but the scan job must complete without waiting for ML inference.

The existing local CLIP/Transformers.js stack is reused for tags. No second model process or external AI service is introduced.

## 1. Qeo AI Tags

### 1.1 Separate tag subsystem

Tags are intentionally separate from `categories`.

Categories remain coarse classification/review concepts and continue to support category album sync. Tags are fine-grained organizational/search metadata for Library.

### 1.2 Curated vocabulary

AI may only suggest tags from a maintained curated vocabulary. Vocabulary v1 contains a stable code-defined set in the 60–100 tag range, grouped around content, people/life, objects, scenes/places, and utility/search concepts. Representative tags include:

- content: `screenshot`, `document`, `receipt`, `menu`, `text`, `design`, `presentation`, `diagram`
- people/life: `family`, `baby`, `child`, `group`, `portrait`
- objects: `car`, `computer`, `phone`, `food`, `drink`
- places/scenes: `indoor`, `outdoor`, `beach`, `city`, `nature`, `travel`
- utility: `qr-code`, `chat`, `social-media`

The complete v1 vocabulary is committed as one versioned source file. Any change to the AI vocabulary increments `taxonomy_version`, so a deliberate vocabulary change can trigger retagging.

Manual user-created tags are allowed even when not present in the curated AI vocabulary. Manual tag names are trimmed and normalized to a lowercase hyphenated slug for uniqueness/search, while retaining a user-facing display name. `#tag` search is case-insensitive and addresses the normalized slug.

### 1.3 Schema v3

Add:

```sql
CREATE TABLE tags (
  id TEXT PRIMARY KEY,
  slug TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  created_at INTEGER NOT NULL
);

CREATE TABLE photo_tags (
  photo_id TEXT NOT NULL REFERENCES photos(id) ON DELETE CASCADE,
  tag_id TEXT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  confidence REAL,
  source TEXT NOT NULL CHECK(source IN ('ai','manual')),
  state TEXT NOT NULL CHECK(state IN ('active','removed')),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY(photo_id, tag_id)
);

CREATE INDEX photo_tags_tag_photo_idx ON photo_tags(tag_id, photo_id);
CREATE INDEX photo_tags_photo_state_idx ON photo_tags(photo_id, state);

CREATE TABLE photo_tag_state (
  photo_id TEXT PRIMARY KEY REFERENCES photos(id) ON DELETE CASCADE,
  tagged_etag TEXT,
  model_id TEXT NOT NULL,
  taxonomy_version TEXT NOT NULL,
  tagged_at INTEGER NOT NULL
);

CREATE INDEX photo_tag_state_etag_idx ON photo_tag_state(tagged_etag);
```

### 1.4 Tag precedence and retagging

User decisions override AI until the user explicitly changes them.

- AI suggestion creates/updates `source='ai', state='active'` only when there is no manual decision for that photo/tag.
- Manual add stores `source='manual', state='active'`.
- Manual remove stores `source='manual', state='removed'`.
- Retagging must never resurrect a manually removed tag.
- Retagging must never overwrite a manually added tag.
- On successful retag, previous `source='ai'` rows for that photo are replaced by the new AI result set; manual rows are preserved unchanged.

This gives the current model/taxonomy ownership of AI-generated rows without losing user corrections.

### 1.5 Batch + incremental tagging

Add a persistent `tag-photos` job assigned to the ML lane.

A photo requires tagging when any of these are true:

- it has no `photo_tag_state` row;
- current photo ETag differs from `tagged_etag`;
- configured CLIP model id differs from `model_id`;
- current vocabulary version differs from `taxonomy_version`.

Initial upgrade exposes a `Generate AI Tags` action to backfill the full library. Afterward, Full/Incremental Scan may enqueue `tag-photos`; the ML job itself selects only photos needing work.

The job uses cached thumbnails and the existing local zero-shot image classification pipeline. It classifies an image against the complete curated vocabulary in one model call, sorts by score, and stores at most the top five labels whose score meets the v1 minimum score constant. The score threshold is a named/versioned tagging constant in the vocabulary module so tuning it requires an explicit taxonomy/tagging version change rather than an invisible behavior change.

### 1.6 Failure handling

Per-photo failures must not waste an entire long-running backfill:

- Graph `404 itemNotFound`: mark the photo remote-deleted/stale, count it as processed, continue.
- isolated thumbnail decode/model inference failure: do not write a valid `photo_tag_state` for that photo, emit a worker warning, count the attempt as processed for the current job, and continue. A later run retries it.
- database corruption, model startup failure, or other systemic failures: fail the job.

A successful tag write and its `photo_tag_state` update must be transactional per photo so a crash cannot mark an incomplete tag set as current.

Rerunning the job processes photos still lacking a valid `photo_tag_state` for the current ETag/model/taxonomy.

## 2. Library Search and Filters

Existing server-side SQLite pagination remains in place.

### 2.1 Search syntax

The search box accepts free text plus tag tokens beginning with `#`.

Examples:

```text
#screenshot
#receipt #document
invoice #document
iphone #family #outdoor
```

Semantics:

- free text searches existing fields plus source-identity fields: filename, path, camera make/model, created/modified user/device/application;
- each valid `#tag` token requires an active tag match by normalized tag slug;
- multiple `#tags` use AND semantics;
- free text and tag filters are also combined with AND;
- active tags from either `ai` or `manual` source are searchable;
- `state='removed'` tags and remote-deleted photos never match Library results.

### 2.2 Tag filter UI

Library exposes a quick tag filter showing active tags and counts over non-deleted photos. Clicking a tag adds/removes it from the active query.

The tag filter and search syntax operate on SQLite only and must not call Microsoft Graph.

## 3. Add to Existing OneDrive Album

### 3.1 Graph behavior

Add support for listing existing OneDrive album bundles, then reuse the existing album-child add operation.

Library flow:

1. User opens Photo Detail.
2. Selects `Add to album`.
3. App loads existing OneDrive Photos albums.
4. User searches/selects one album.
5. App adds the current drive item to that album.

This flow must not create a new album.

The add action must be safe to repeat. Where Graph identifies that the item is already a member, the app treats that condition as a successful no-op rather than creating local failure state.

### 3.2 Album list cache

The server may cache the album list in process memory for five minutes to reduce repeated Graph requests while browsing many photos. The cache is disposable and must not become authoritative persistent state.

If the selected album becomes stale/deleted and Graph returns `itemNotFound`, invalidate/refresh the album list and show a user-facing failure instead of blindly retrying.

## 4. Single-Photo Delete from Library

### 4.1 UX

Photo Detail includes a destructive `Delete photo` action. The UI must require explicit confirmation such as:

`Move IMG_1234.JPG to OneDrive Recycle Bin?`

There is no separate mark-for-delete/review queue for this single-photo flow.

### 4.2 Safety contract

Deletion service must:

1. Load the latest local photo row on the server at mutation time and read `photos.etag`.
2. Fetch the current Graph item.
3. Compare current Graph ETag with that server-loaded local ETag.
4. Abort without deleting if either ETag is missing or they do not match.
5. Use normal Microsoft Graph `DELETE` only, with the matched ETag supplied as the conditional preflight/header where supported by the existing drive API.
6. Write `deletion_log`.
7. Mark the local photo/drive node remote-deleted.
8. Remove it from Library results immediately.

The Graph delete plus local deletion-log/state update cannot be one distributed transaction. If Graph delete succeeds but local persistence fails, the next scan must reconcile the item as remote-deleted; the API must report the local persistence failure rather than attempting a second destructive request blindly.

`DEMO_MODE=1` must continue to block destructive OneDrive actions.

No permanent-delete endpoint or Graph path may be added.

Unlike duplicate cleanup, single-photo manual deletion does not require SHA-256 duplicate verification because the user is explicitly deleting that exact photo.

## 5. Source Identity Metadata

### 5.1 Graph scan fields

Extend scan metadata selection/mapping with `createdBy` and `lastModifiedBy` identity sets.

Store best-effort identity values on `photos`:

```text
created_by_user_name
created_by_device_name
created_by_device_id
created_by_application_name
created_by_application_id

modified_by_user_name
modified_by_device_name
modified_by_device_id
modified_by_application_name
modified_by_application_id
```

All fields are nullable. On a scanned item upsert, these columns reflect the current Graph response; an unavailable identity component is stored as null rather than inferred.

### 5.2 Semantics

- `Camera` means capture device from photo metadata.
- `Uploaded/created by` means Graph `createdBy` identity information.
- `Last modified by` means Graph `lastModifiedBy` identity information.
- If Microsoft does not return device identity, do not infer it.
- Missing source fields are omitted from the UI.

A Full Scan after upgrade backfills these fields for existing items where Graph exposes them.

## 6. Photo Detail UX

Photo Detail becomes the primary per-photo organization surface.

Recommended structure:

```text
Photo preview

Tags
  #family #outdoor #iphone
  Add tag

Album
  Add to album

Metadata
  Captured
  Camera
  Uploaded/created by
  Last modified by
  dimensions/exposure/etc.

Technical
  ETag
  QuickXorHash
  SHA-256

Danger zone
  Delete photo
```

AI and manual tags should be visually distinguishable where useful, but search treats all active tags equally.

Technical hashes move out of the primary metadata block so user-facing organization data receives higher visual priority.

## 7. API Boundaries

Use a small write-action surface for Library operations, for example:

- `POST /api/photos/action`
  - `add-tag`
  - `remove-tag`
  - `add-to-album`
  - `delete`
- `GET /api/albums` for read-only existing album discovery
- existing job APIs for `tag-photos` creation/status

Exact route naming may follow existing repository conventions during implementation, but the capabilities must remain separated into read-only album discovery, explicit photo mutations, and persistent background ML work.

All mutation payloads are server-validated. The client supplies photo ids/tag input/album ids only; authoritative drive item ids and ETags are reloaded from local state on the server.

## 8. Migration and Upgrade

Schema version becomes v3.

Migration from v2 must be in-place and preserve all existing:

- photos and hashes;
- duplicate review state;
- categories/classification review state;
- album sync state;
- authentication/token cache;
- settings.

No `/data` reset is required or permitted as part of normal upgrade instructions.

Upgrade flow:

1. rebuild/start v0.3 containers;
2. migration runs automatically;
3. run one Full Scan to backfill `createdBy`/`lastModifiedBy` where available;
4. start `Generate AI Tags` once for initial tag backfill;
5. future scans enqueue incremental tag work without blocking scan completion.

## 9. Testing Strategy

Tests must cover at minimum:

### Database/migration
- v2 -> v3 migration preserves old records and adds new nullable identity/tag structures.
- tag indexes/constraints enforce expected uniqueness.

### Tags
- curated AI tags are persisted with confidence.
- maximum AI-tag count/threshold behavior.
- successful retag replaces old AI rows while preserving manual rows.
- manual add overrides AI.
- manual remove survives retagging.
- manual tag normalization/uniqueness is case-insensitive through normalized slugs.
- model/taxonomy/ETag changes select the photo for retagging.
- unchanged tagged photos are skipped.
- failed per-photo inference does not write current `photo_tag_state` and is retried later.
- tag rows and tag state update transactionally per photo.
- `tag-photos` is claimable only by the ML lane.

### Search
- single `#tag` filtering.
- multiple tags use AND semantics.
- free text + tags combine with AND.
- source identity fields participate in free-text search.
- removed tags and deleted photos remain excluded.
- tag counts exclude removed/deleted rows.

### Albums
- list existing albums.
- add current item to an existing album.
- repeated/already-member add is a successful no-op where Graph exposes that condition.
- stale album `itemNotFound` is surfaced and refreshable.
- Library action never creates a new album.

### Delete
- UI requires confirmation.
- service reloads authoritative local item/ETag server-side and performs Graph item fetch/ETag preflight.
- missing or changed ETag aborts deletion.
- successful action uses normal Graph delete, writes deletion log, and marks local remote deletion.
- Graph-success/local-persistence-failure is not followed by a blind second delete.
- DEMO_MODE blocks deletion.
- no permanent-delete path is introduced.

### Source identity
- created/modified user/device/application map correctly when present.
- missing device data becomes null and is not inferred.

### Runtime/CI
- full unit/component suite.
- lint, typecheck, production build.
- production Docker build.
- web health/root smoke.
- core worker startup smoke.
- ML worker startup smoke including `tag-photos` lane ownership.
- Gitleaks.

## 10. Acceptance Criteria

v0.3 is complete when:

1. Library users can add the current photo to an existing OneDrive Photos album without creating a new album.
2. A full-library local AI tag backfill can run independently on the ML worker.
3. Future scans result in only new/changed/outdated photos needing retagging.
4. Users can add/remove tags manually and AI reruns respect those decisions.
5. Library can search/filter by Qeo tags quickly using SQLite, including multiple-tag AND queries.
6. A user can explicitly delete one Library photo into OneDrive Recycle Bin with server-side ETag safety and deletion logging.
7. Photo Detail displays capture metadata plus best-effort OneDrive created/modified identity data without guessing missing devices.
8. Existing duplicate safety, category album sync behavior, OAuth model, persistent `/data`, and no-permanent-delete guarantees remain intact.
